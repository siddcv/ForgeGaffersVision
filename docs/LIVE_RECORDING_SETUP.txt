GAFFER'S VISION: LIVE RECORDING SETUP (MAC)
===========================================

This gets the pipeline running live on a Mac with a phone as the camera, records each session,
and sends the recordings back so we can check the counts. First-time setup takes about 30 minutes;
after that, a session is one command.

1. BEFORE YOU START
-------------------
[ ] A Mac you can install software on (Apple Silicon is best)
[ ] Camo installed on both the phone and the Mac, plus a cable to connect them (steadier than Wi-Fi)
[ ] A phone stand, or something to prop the phone on, low and in front of the player
[ ] A ball, a player, and about 3 m of clear floor in front of the phone
[ ] A second person to count tick-tocks by hand during each drill
[ ] Internet for the first run only (the models download once; after that it runs offline)


2. ONE-TIME SETUP
-----------------
[ ] Install Python 3.12. Check with:
        python3.12 --version
    If it is missing and you cannot install apps, use uv instead (no admin rights needed):
        curl -LsSf https://astral.sh/uv/install.sh | sh
        uv venv --python 3.12 ~/.venvs/gaffers-vision
    (then skip the python3.12 -m venv line below)

[ ] Get the code on the develop branch (it has the head tracking):
        git clone https://github.com/siddcv/ForgeGaffersVision.git
        cd ForgeGaffersVision
        git switch develop
    Already cloned? Run: git fetch, then git switch develop, then git pull

[ ] Create and activate the environment, then install the packages:
        python3.12 -m venv ~/.venvs/gaffers-vision
        source ~/.venvs/gaffers-vision/bin/activate
        pip install -r requirements.txt
    requirements.txt was made on Windows. If one pinned version fails to install, install that
    package without the version (e.g. pip install mediapipe) and tell Siddharth which one it was.

[ ] Run the tests (should all pass, about 180):
        python -m pytest

[ ] Open Camo on the phone and on the Mac and confirm the Mac shows the phone's camera.

Every later session: open a terminal, then
        cd ForgeGaffersVision
        source ~/.venvs/gaffers-vision/bin/activate
        git pull


3. CAMERA PLACEMENT
-------------------
[ ] Phone in front of the player, facing them (front-facing view), lens low: about knee to hip height
[ ] About 2-3 m away, so the legs, feet and ball are always in frame (whole body is better)
[ ] Phone held still; do not move it during a drill
[ ] Even light, no bright window behind the player
[ ] Write down the height and distance (in metres) for each setup you try


4. RUNNING A LIVE SESSION
-------------------------
[ ] Start it:
        python -m src.live --source 0
        python -m src.live --source 0 --rotate 90
    If the window shows the Mac's own camera, quit and try --source 1, then --source 2.

[ ] First run only:
    - macOS asks for camera access for Terminal (or VS Code). Allow it, then run the command again.
    - The models (pose, face, ball) download and the ball detector is converted once; this takes
      a minute or two and needs internet.

[ ] Fix the picture if needed:
        --rotate 90        image is sideways (also 180 or 270)
        --flip             image is mirrored
    Check left and right: tap only with the player's LEFT foot; the LEFT contact count should go up.
    If the right one goes up instead, add --flip.

[ ] The window opens in READY: the overlay runs but nothing is counted or recorded yet.
    Use this time to place the phone and the player.

[ ] START is grey ("STEP INTO FRAME") until the whole player, head to toe, and the ball are
    in frame, away from the edges, for half a second. The orange text above the button says
    what is missing (head, left foot, right foot, ball). Move the phone back or the player
    in until START turns green.

[ ] During the countdown and the drill, "RECENTER YOURSELF" appears if the player's head or a
    foot has been out of frame for half a second. Nothing pauses; step back into the middle and
    it goes away. (The ball rolling away is not a framing problem: it counts as lost control.)

[ ] Each drill:
        START button (or space)   3-second countdown, then counts reset and recording starts
                                  (red REC and the drill time show top-right)
        STOP button (or space)    ends the drill: its recording and summary are saved, and the
                                  terminal prints where. Back to READY for the next drill.
        q or Esc                  quit (a running drill is saved first)
    Say the hand count out loud after each STOP and write it down with the drill's time.

[ ] Do 3-4 short drills of about 20 s each, one START/STOP per drill. Each drill gets its own
    recording, so each matches one hand count. Keep one camera position per set of drills.


5. WHAT TO CHECK AND WRITE DOWN
-------------------------------
Status line (bottom of the window):
[ ] At start the terminal prints the camera's size and frame rate ("Camera: 720 x 1280 (portrait)
    ... Camera is delivering 30.0 fps"). A landscape WARNING means the framing is off: fix it
    before recording (Camo portrait setting, or --rotate 90).
[ ] fps, proc (processing ms) and lag after it settles.
    Good: above 15 fps and lag under about 150 ms. Below 10 fps, note it.

On screen during the drills:
[ ] Orange box stays on the ball most of the time. Note when it loses it (blur, ball against
    shoes, lighting).
[ ] Cyan box follows the feet with the ball inside it.
[ ] Top-left mostly says TRACK; SEARCH only briefly when the ball is hidden. Note long SEARCH
    while the ball is clearly visible.
[ ] Tick-tock count vs the hand count, per drill (e.g. "screen 31, hand 34").
[ ] Left/right split matches the feet; note any swaps.

Try each of these once, on purpose:
[ ] Lose the ball properly (let it roll away). Lost control should appear.
[ ] Stop with the ball still between the feet for 2-3 s. Note whether it wrongly says lost control
    (known issue).
[ ] A few double touches with the same foot. These should count as contacts, not tick-tocks.
[ ] Look down at the ball for more than 1 s. Note whether head-down reacts.
    Head-down is not calibrated for this setup yet: it may show HEAD DOWN all the time. Write down
    the pitch number when the player looks straight ahead and when they look at the ball; that is
    what the calibration needs.

How it feels:
[ ] "contact" flashes right away; "TICK-TOCK" confirms about 0.4 s later. Is that OK or confusing?
[ ] Which height and distance gave the steadiest ball box?


6. WHAT TO SEND BACK
--------------------
Recordings are saved in:
        data/clips/live/<date>/drill_<date>_<time>.mp4
        data/clips/live/<date>/drill_<date>_<time>.timestamps.csv     (real capture times; keep it with the .mp4)
    (.avi instead of .mp4 if this Mac cannot write .mp4; the terminal says which)
Summaries and events are saved in:
        output/live/drill_<date>_<time>.json
Each recorded drill also adds a row to data/manifest.csv (name, date, fps, resolution,
orientation, drill window). Fill in its player, camera height/distance, lighting and split
(tune or test) when you file the clip; that file is in git, so commit it with the labels.
The live window's view (overlay, counts, REC), as a video that plays at real speed:
        output/live/drill_<date>_<time>_overlay.mp4     (for watching only: label and replay the raw .mp4)

[ ] Your notes from section 5, with the drill times
[ ] One clean drill and one messy drill: each .mp4 AND its .timestamps.csv
[ ] The matching output/live/*.json files, and the _overlay.mp4 videos if something looked wrong

Send the files by cable, AirDrop or a shared drive, not through a messaging app (it re-compresses
the video). Clips are not in git, so do not commit them.


7. TROUBLESHOOTING
------------------
"Could not open camera 0"
    Try --source 1 or 2. Check that Camo is open on both devices and the phone is connected.

Window opens but stays black, or the camera is refused
    System Settings > Privacy & Security > Camera: allow Terminal (or VS Code), then restart it.

pip install fails on one package
    Install that package without the version number and report which one.

No recording saved after STOP
    Read the terminal: it prints "Recording to ..." at START and "Saved ... and the recording ..."
    at STOP. "Could not open a video writer" means this Mac's OpenCV cannot write video; send the
    message to Siddharth and use --no-record meanwhile. Recordings are in data/clips/live/, which
    git ignores, so they do not show up in git status (VS Code shows the folder greyed out).
    Only drills between START and STOP are recorded; nothing is saved while the window says READY.

START stays grey even though the player and ball look in frame
    Read the orange text above the button. "ball not found": the detector cannot see the ball
    (move it between the feet, better light). "head not in frame": leave some space above the
    head. If it still will not enable, run with --no-framing-check and tell Siddharth.

Image is sideways or mirrored
    --rotate 90 / 180 / 270, and --flip. Recheck left/right with the left-foot-only test.

Very low fps (below 10)
    Close other apps. Note the number anyway; it is useful data.

"ModuleNotFoundError: No module named 'src'"
    Run the commands from inside the ForgeGaffersVision folder.

Something else
    Copy the full error text from the terminal and send it to Siddharth.
